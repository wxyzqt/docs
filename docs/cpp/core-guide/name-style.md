# 命名规范和代码风格

## 命名规范

### 类型名

- **建议**：使用大驼峰（PascalCase），如 MyClass、Vector2D。
- **说明**：模板参数建议用单个大写字母或 PascalCase，如 `typename T` 或 `typename ValueType`。

### 变量、函数、参数名

- **建议**：使用小驼峰（camelCase），如 myVariable、calculateArea()、inputValue。
- **说明**：布尔变量建议用 is、has、can 等前缀，如 isValid、hasData。

### 常量名

- **建议**：全大写加下划线，如 MAX_SIZE、DEFAULT_TIMEOUT。
- **说明**：对于类内常量，可用 k 前缀加大驼峰，如 kMaxSize。

### 命名空间名

- **建议**：简短小写字母，如 math、util。
- **说明**：避免与标准库命名空间冲突，必要时可加项目前缀。

### 避免下划线开头

- **建议**：不要使用单下划线或双下划线开头的标识符（如 \_internal 或 \_\_reserved），以避免与实现保留名称冲突。
- **说明**：遵循 C++ 标准，所有以下划线开头的标识符均为实现保留。

### 命名应表达清晰含义

- **建议**：避免晦涩缩写，名称要能准确表达用途和含义。
- **说明**：必要时可适当缩写，但需团队达成共识。

### 文件名与类名一致

- **建议**：文件名建议与类名保持一致，便于查找和维护。
- **说明**：文件名建议全小写，单词间用下划线分隔，如 my_class.h。

## 代码风格

### 每个声明单独一行

```cpp
int width;
int height;
```

### 一致的缩进

推荐 4 个空格缩进，不使用 Tab，避免 tab 在不同编辑器上的差异。

### 统一花括号风格

选择一种花括号风格（如 K&R 或 Allman），团队内部保持一致。

在类、函数、控制语句等所有结构体上统一风格。

```cpp
void foo() {
    // ...
}
```

### 避免魔法数字

使用具名常量替代魔法数字。

所有出现多次的常量都应具名。

```cpp
const int MaxRetries = 3;
```

### 头文件保护

使用 include guard 或 #pragma once(事实标准)。

include guard 命名应唯一且规范，如 PROJECT_MODULE_CLASS_H。

```cpp
#pragma once
// 或
#ifndef MYCLASS_H
#define MYCLASS_H
// ...
#endif
```

### 注重可读性

代码应易于阅读和维护，变量、函数、类的命名要清晰。

适当添加空行分隔逻辑块，避免过长函数。

## 其他建议

### 注释说明“为什么”

注释应解释代码背后的原因，而不是描述代码做了什么。

复杂逻辑、特殊处理、设计决策等应有详细注释。

### 避免全局变量

尽量减少全局变量的使用，提升代码可维护性。

如需全局状态，优先考虑单例、命名空间内静态变量等替代方案。

### 保持风格一致

团队内部应统一代码风格和命名规范。

可制定代码风格检查工具（如 clang-format、cpplint）辅助执行。
